# So What is CSRF?
It is a class of vulnerability that can impact web applications. Typically the attack looks like the following.
1. First a  particular set of conditions must be true for an attacker to exploit a CSRF vulnerability
	- **A relevant action.** There is an action within the application that the attacker has a reason to induce. This might be a privileged action (such as modifying permissions for other users) or any action on user-specific data (such as changing the user's own password).
	- **Cookie-based session handling.** Performing the action involves issuing one or more HTTP requests, and the application relies solely on session cookies to identify the user who has made the requests. There is no other mechanism in place for tracking sessions or validating user requests.
	- **No unpredictable request parameters.** The requests that perform the action do not contain any parameters whose values the attacker cannot determine or guess. For example, when causing a user to change their password, the function is not vulnerable if an attacker needs to know the value of the existing password.
2. If all these conditions are true an attacker must then enumerate the application in question to hopefully discover a PoC expoit and deliver it to the victim
	- URL Based PoC
		- If a web page has incorrectly used GET requests for an endpoint which performs an action which changes the state of an application you can typically deliver the PoC through the use of a URL.
		- Can be delivered through phising / watering hole style attacks
	- HTML Based PoC
		- If the page properly uses POST requests for the vulnerable action, an attacker can craft their own HTML page, host it and ensure there is a malicious form with hidden inputs and program it to auto submit. 
		- You can deliver this exploit by tricking an victim to visit your malicious website through something like phishing.

# Exploitation Examples
## URL Based 
### Exploit Template
```html
<img src="https://vulnerable-website.com/email/change?email=pwned@evil-user.net">
```
It is rare, but if an application uses get requests for sensitive stateful operations you can use a simple link to exploit a CSRF vulnerable application. You can embed the link in an HTML element or deliver it in a phishing attack.

## HTML Based
### Exploit Template
You can use the following snippit as a starting point for building a HTML based CSRF PoC
```html
<form action="https://vulnerable_endpoint_on_target">
    <input type="hidden" name="email" value="Desired value for vulnerable email parameter">
</form>
<script>
        document.forms[0].submit();
</script>
```
If you can host this form and direct a victim to visit it, a request will be sent to the *vulnerable_endpoint_on_target* along with the victims cookies which will in turn perform some sort of privileged action on the *vulnerable application*
# Remediation & Prevention

**CSRF tokens** - A CSRF token is a unique, secret, and unpredictable value that is generated by the server-side application and shared with the client. When attempting to perform a sensitive action, such as submitting a form, the client must include the correct CSRF token in the request. This makes it very difficult for an attacker to construct a valid request on behalf of the victim.


```html
<form name="change-email-form" action="/my-account/change-email" method="POST"> <label>Email</label> 
<input required type="email" name="email" value="example@normal-website.com"> 
<input required type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u"> 
<button class='button' type='submit'> Update email </button> 
</form>
```
> These are usually delivered as a hidden parameter in an HTML Form
> You can also send a CSRF token as a HTTP Header

**SameSite cookies** - SameSite is a browser security mechanism that determines when a website's cookies are included in requests originating from other websites. As requests to perform sensitive actions typically require an authenticated session cookie, the appropriate SameSite restrictions may prevent an attacker from triggering these actions cross-site. Since 2020, Chrome enforces `Lax` SameSite restrictions by default. As this is the proposed standard, we expect other major browsers to adopt this behavior in future.
    
**Referer-based validation** - Some applications make use of the HTTP Referer header to attempt to defend against CSRF attacks, normally by verifying that the request originated from the application's own domain. This is generally less effective than CSRF token validation.
## Common Pitfalls When Protecting Against CSRF
- Sometimes an app will only validate POST requests so an attacker can try a GET request to bypass validation
- Sometimes an application will skip validation if you don't provide the parameter
- Token not tied to user session. Sometimes an application has a pool of CSRF Tokens that are valid and gives them out to clients. If this is the case a malicious user can obtain a CSRF token from the pool by visiting the site and then abuse if to bypass the CSRF token check when exploiting a CSRF bug.
- If a CSRF token is not tied to a session token then you can theoretically use anyone's token for example one that you obtained yourselfF
